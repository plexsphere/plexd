# CI Workflow

The `.github/workflows/ci.yml` workflow runs lint checks, unit tests, and integration tests on every pull request. All jobs run in parallel with no inter-job dependencies. `lint` and `integration-test` run on `ubuntu-latest`; `unit-test` runs on Linux, Windows and macOS.

## Trigger Events

| Event               | Filter | Description                                    |
|---------------------|--------|------------------------------------------------|
| `pull_request`      | (all)  | Runs on opened, synchronized, and reopened PRs |
| `workflow_dispatch` | —      | Manual run against any branch                  |

The workflow does not run on pushes to `main`. A `pull_request` run checks out the merge result rather than the branch head, so the commit that lands on `main` is the commit CI already tested; repeating the run after the merge tests it a second time. Use `workflow_dispatch` to verify `main` on demand — after a merge whose base had moved since the PR run, for example.

A branch without an open PR does not trigger the workflow on push.

## Jobs

All jobs use `actions/checkout@v4` and `actions/setup-go@v5` with Go 1.26, pinned to full SHA hashes for supply-chain hardening. Each job sets `timeout-minutes` to prevent runaway CI from consuming unlimited minutes. Module caching is handled automatically by `setup-go@v5` using `go.sum` as the cache key.

### lint

Static analysis and dependency verification.

| Step                   | Command / Action                                           | Purpose                              |
|------------------------|------------------------------------------------------------|--------------------------------------|
| Checkout               | `actions/checkout@v4`                                      | Clone repository                     |
| Setup Go               | `actions/setup-go@v5` (`go-version: '1.26'`)              | Install Go with module caching       |
| Verify dependencies    | `go mod verify`                                            | Validate checksums against `go.sum`  |
| Run go vet             | `go vet ./...`                                             | Built-in static analysis             |
| Install staticcheck    | `go install honnef.co/go/tools/cmd/staticcheck@latest`     | Install advanced static analyzer     |
| Run staticcheck        | `staticcheck ./...`                                        | Detect bugs and deprecated patterns  |
| Run golangci-lint      | `golangci/golangci-lint-action@v9` (`version: v2.12.2`)    | Aggregated linter suite              |

The `golangci-lint` action runs golangci-lint v2 (pinned via the `version` input), configured by `.golangci.yml` in the repository root. The config restores the default exclusions that golangci-lint v1 applied implicitly, since v2 dropped them. golangci-lint v2 is required because v1 binaries are built with Go 1.24 and refuse to run against the `go 1.26.0` directive in `go.mod`.

The `-count=1` flag disables test caching to ensure every CI run exercises all tests. The `-race` flag enables the Go race detector.

The privileged Linux step is gated on `if: runner.os == 'Linux'` and runs `TestNftablesController_Real`, `TestNftablesController_RealTraffic` and `TestNftablesController_RealConnLog` as root. All three ask for `PLEXD_TEST_REAL_NFTABLES=1` on top of an effective uid of 0, and the step sets it: the variable keeps `sudo go test ./...` on a developer's host from running them there. The traffic test creates its TUN device, its address and its rules in a fresh network namespace and runs there the checks `TestPFController_RealTraffic` and `TestWFPController_RealTraffic` run on macOS and Windows, the round-trip probe's among them: with no rule naming port 7911, N's probe to P's port 7911 leaves, and P's probe from port 7911 reaches an echo on N's port 7911, whose answer leaves. The connection logging test does the same with the checks of `TestPFController_RealConnLog`, and binds NFLOG group 28772 in that namespace, not in the runner's. Every other test in `./internal/policy/` that calls the nftables controller runs inside a network namespace of its own, so a privileged run leaves the host's tables alone. The step runs under `set -o pipefail` and fails unless the output holds `--- PASS: TestNftablesController_Real`, `--- PASS: TestNftablesController_RealTraffic` and `--- PASS: TestNftablesController_RealConnLog`, so a skip of any of them fails it. Each pattern ends in a space, so the other tests' lines cannot stand in for the first one. The step then runs `TestNetlinkVPNController_RealLinks` and `TestNetlinkRouteController_RealRoutes` in `./internal/bridge/` as root, which ask for `PLEXD_TEST_REAL_LINKS=1` on top of an effective uid of 0 for the same reason, with `TestRTTProbe_RealAnswersOnlyTheMeshInterface` in `./internal/wireguard/` under the same gate, and fails unless its output holds `--- PASS: TestNetlinkVPNController_RealLinks`, `--- PASS: TestNetlinkRouteController_RealRoutes` and `--- PASS: TestRTTProbe_RealAnswersOnlyTheMeshInterface`. The round-trip probe test builds a node, a mesh peer and a host on another network in namespaces of their own, and wants the probe's socket, bound to the mesh interface, to answer the peer and not a request from a spoofed mesh source that arrives on the other network's link, after it shows that a socket bound to the mesh IP alone answers that request. The route test adds a route through a dummy link in a namespace of its own and wants `RemoveRoute` to delete it from the kernel, and wants the kernel's route to the link's own network kept after `AddRoute` and `RemoveRoute` of that network. In a network namespace of its own the test creates the xfrm interface of an `ipsec` tunnel with the id 2694881506 and the persistent tun device of an `openvpn` tunnel, and wants them of type `xfrm` with that id and `tuntap` with the persist flag. It creates a WireGuard tunnel interface with a kept key, wants a second one on the same port to fail with `ErrListenPortInUse` and leave no link, and wants `RemoveTunnelInterfaces` with the three site-to-site prefixes to delete all three kinds and keep a WireGuard link named `wg-other0`. It is the only proof that netlink creates the two links the way the `ip` commands of the measurement behind [#212](https://github.com/plexsphere/plexd/issues/212) did; see [Tunnel Providers](../bridge/tunnel-providers.md). It passes the module and build caches through `sudo env` and resolves the toolchain with `$(command -v go)`, as the macOS step does, for the reasons given below.

The privileged macOS step is gated on `if: runner.os == 'macOS'` and runs only there. `TestPFController_Real`, `TestPFController_RealTraffic`, `TestPFController_RealConnLog` and `TestPFController_RealMeshSourceRewrite` also ask for `PLEXD_TEST_REAL_PF`, which the step sets: root alone would let `sudo go test ./...` on a developer's Mac enable pf on their host and load a real anchor. The traffic test and the connection logging test each create a utun of their own and send traffic through it, under rules that name that utun alone. In the connection logging test the controller also creates `pflog0` when the Mac has none and reads it through `/dev/bpf`. The mesh source rewrite test creates a mesh utun and a provider's and a tunnel's utun beside it, switches `net.inet.ip.forwarding` on and restores it, and forwards packets between them through the rewrite's lines (see [pf & WFP Firewall Controllers](../networking/pf-wfp-firewall.md#tests)). The traffic test is the only proof of what a Mac's pf lines let out and back in, the two stateless round-trip probe lines included, the connection logging test the only proof of the line numbers pf reports, and the mesh source rewrite test the only proof that a tag set on the way in reaches the `nat` line on the way out and that `nat pass` skips the filter rules, so the step runs under `set -o pipefail` and fails unless the output holds `--- PASS: TestPFController_RealTraffic`, `--- PASS: TestPFController_RealConnLog` and `--- PASS: TestPFController_RealMeshSourceRewrite`, a skip included. `TestScutilRegistrar_Real` in `./internal/meshdns/` asks for `PLEXD_TEST_REAL_RESOLVER` on top of root, and the step sets that as well: the test writes configd's dynamic store and resolves through mDNSResponder to a resolver on 127.0.0.1 beside a real utun, so it changes the host's resolver configuration while it runs, and root alone would let `sudo go test ./...` on a developer's Mac change their resolver. Creating a utun device needs root, and so do altering the routing table and the forwarding sysctl, so the eight macOS tests against the real kernel skip in the unprivileged run and would otherwise never execute. `TestSessionHelper_PTYBelongsToLoginUser` and `TestSessionHelper_RefusedPTYKeepsItsOwner` start a shell as uid 65534 and hand it the pty, which needs root as well; they skip on every other runner, so this step is where CI exercises the session helper switching users. `TestWGControllers_RealUTUN` creates its utuns through the bridge controllers and routes over them; its access subtest also wants the controller's `utunN` name, the address `10.255.252.1` and the on-link route of an addressed access utun on port 51993, and `ErrListenPortInUse` from a second create on that port. `TestPeerRoutes_RealUTUN` sets a WireGuard manager up at `10.99.0.1` in `10.99.0.0/24` on a utun of its own, with `DarwinRouteController` as its `PeerRouter`, runs the reconcile handler with a peer at `10.99.0.2` whose `routed_subnets` are `["10.20.0.0/16"]`, and wants the peer's allowed IPs `10.99.0.2/32` and `10.20.0.0/16` and `route -n get 10.20.0.1` to name the utun; a second run without the member wants both gone. It is the only proof that macOS accepts the [peer routes](../networking/wireguard.md#routed-subnets), without traffic, so the step also fails unless the output holds `--- PASS: TestPeerRoutes_RealUTUN`. `sudo` resets the environment, so the step passes the module and build caches through `sudo env` and resolves the toolchain with `$(command -v go)` before `sudo` replaces `PATH`; root then reuses what the previous step downloaded and built. `-v` is what makes a skip visible in the log rather than passing as a bare `ok`.

The Wintun step is the Windows counterpart, gated on `if: runner.os == 'Windows'`. It needs no `sudo`: that runner is already elevated, which is why the gate of its three tests, `TestWindowsController_RealWintun`, `TestWGControllers_RealWintun` and `TestPeerRoutes_RealWintun`, is `PLEXD_TEST_REAL_WINTUN` rather than a privilege check. Without a separate variable they would also run inside `Run unit tests` and create real adapters there. They write the embedded `wintun.dll` beside their own binaries, so the step fetches nothing, and `-v` makes a skip visible here too. `TestPeerRoutes_RealWintun` also alters the routing table, so it asks for `PLEXD_TEST_REAL_ROUTES` as well, which the step sets beside `PLEXD_TEST_REAL_WINTUN`. It runs the checks of `TestPeerRoutes_RealUTUN` over a Wintun adapter with `WindowsRouteController` as the `PeerRouter`, and reads the route for `10.20.0.0/16` on the adapter's LUID the way `TestWindowsRouteController_Real` reads its routes. It is the only proof that Windows accepts the [peer routes](../networking/wireguard.md#routed-subnets), so the step writes the test output to `real-wintun.txt` under `RUNNER_TEMP`, exits with `go test`'s status when it failed, and fails unless the output holds `--- PASS: TestPeerRoutes_RealWintun`, a skip included.

The route step is gated the same way, on `PLEXD_TEST_REAL_ROUTES`, and for the same reason: without its own variable the test would alter the runner's routing table from inside `Run unit tests`. The WFP step carries `PLEXD_TEST_REAL_WFP` for the same reason: without its own variable its five tests would create Wintun adapters, install filters and NetNat objects and turn on a filter engine setting of the whole host from inside `Run unit tests`. `TestWFPController_RealTraffic` and `TestWFPController_RealConnLog` create the Wintun adapter `plexd-fwtest` and inject unsolicited packets into it, which the Windows Firewall would block on its own, so the step first runs `Set-NetFirewallProfile -All -Enabled False` to turn every firewall profile off. plexd's filters sit in a sublayer of their own and do not depend on the Windows Firewall. The traffic test's round-trip probe checks are the only proof on the real engine that the probe permits at the connect and receive-accept layers pass port 7911 in both directions. `TestWFPController_RealConnLog` runs the connection logging checks `TestNftablesController_RealConnLog` and `TestPFController_RealConnLog` run on Linux and macOS. It turns on a filter engine setting of the whole host, `collect_net_events` and the classify-allow keyword in `match_any_keywords`, which outlives the process, and checks that the controller puts it back after the last logged rule goes and, from the record a crashed run leaves, at the next start. A cleanup puts both options back to their starting values whatever the test's result, and the test stops when the keyword is already set. `TestWFPController_RealNATExemption` creates two Wintun adapters, one at `10.255.243.1/24` that stands for the mesh adapter, and exempts the other from the NetNat object `AddNATMasquerade` creates for `10.255.243.0/24`: it checks the exemption's object and its 169.254 address on the real host, and the mesh source rewrite step below checks the traffic under it (see [pf & WFP Firewall Controllers](../networking/pf-wfp-firewall.md#tests)). The step writes the test output to `real-wfp.txt` under `RUNNER_TEMP` as well, exits with `go test`'s status when it failed, and fails unless the output holds `--- PASS: TestWFPController_RealTraffic`, `--- PASS: TestWFPController_RealConnLog` and `--- PASS: TestWFPController_RealNATExemption`, a skip included.

The mesh source rewrite step carries `PLEXD_TEST_REAL_WINTUN`, `PLEXD_TEST_REAL_ROUTES` and `PLEXD_TEST_REAL_WFP`, the gates of the three things `TestMeshSourceRewrite_RealWintun` does to the runner, for the same reason as the steps above. The test builds a bridge from the production constructors: a `wireguard.MeshRewriter`, the mesh adapter `plexd-rwm` (`10.255.241.1/24`) from a `WindowsController` with `SetMeshRewriter`, the provider `wg-ua-0000c1c1` (`10.255.242.1/24`) through `NewWGAccessController`, the tunnel `wg-s2s-0000c1c1` through `NewWGVPNController`, a `WindowsRouteController` that switches forwarding on between `plexd-rwm` and each of the two others and routes `10.255.240.0/24` into the tunnel, and a `WFPController` for `plexd-rwm` with its chains, its NetNat object and the tunnel's exemption. Its far ends N (`10.255.241.2`), D (`10.255.242.2`) and S (`10.255.240.2`) are wireguard-go devices over channel tuns, with endpoints on `127.0.0.1`. A socket of the test echoes on `10.255.242.1:7002` and takes unsolicited inbound UDP, which the Windows Firewall would block on its own, so the step first runs `Set-NetFirewallProfile -All -Enabled False` itself, as the WFP step does, rather than rely on running after it. Its NetNat objects carry the names the WFP step's NAT tests use, `plexd` and `plexd-exempt-*`, and the test fails before it creates anything when the host holds an object of those names or one that covers its mesh prefix, so the two stay in steps of their own. The test is the only proof of the mesh source rewrite and of the NAT exemption on Windows (see [In-process mesh source rewrite](../networking/wireguard.md#tests)), so the step writes the test output to `real-meshrewrite.txt` under `RUNNER_TEMP`, exits with `go test`'s status when it failed, and fails unless the output holds `--- PASS: TestMeshSourceRewrite_RealWintun`, a skip included.

The resolver step carries `PLEXD_TEST_REAL_RESOLVER` for the same reason: `TestNRPTRegistrar_Real` writes Name Resolution Policy Table rules, a search list and the Group Policy key, signals machine policy changes and binds `127.0.0.1:53`, which changes the runner's resolver configuration while it runs, and without its own variable it would do that from inside `Run unit tests`. The test waits up to 120 seconds for the Group Policy watcher to copy plexd's rules, 20 seconds for the watcher to go quiet, and up to 180 seconds each for the names to resolve and to stop resolving through the Group Policy store, over 8 minutes for those waits alone, so the binary runs with `-test.timeout=15m`, above `go test`'s default of 10 minutes. The step runs the test as LocalSystem, the account plexd's service runs as, through a scheduled task: the DNS Client reads the Group Policy store, and the removal of its key, only after a machine policy change, and on the runner `GenerateGPNotification` called as LocalSystem sent one, while two forced refreshes with `RefreshPolicyEx` from the step's Administrator sent none in four minutes. The task does not inherit the step's environment, so the script it runs sets `PLEXD_TEST_REAL_RESOLVER`. The step prints the test's output as it grows and fails unless that output holds `--- PASS: TestNRPTRegistrar_Real`, so a skip fails it.

The port reservation step carries `PLEXD_TEST_REAL_PORT_RESERVATION` for the same reason: without its own variable its three tests would reserve ports of the host from inside `Run unit tests`, and a reservation outlives a killed test and a reboot. The Windows runner boots with runs of 100 neighbouring ports reserved for TCP and others reserved for UDP, two side by side for each on most boots, as `netsh int ipv4 show excludedportrange` lists them. A bind inside a run fails with `WSAEACCES`, and on port 0 the kernel still hands those numbers out to the protocol that did not reserve them, one after the other and to every process alike. A pick that took a kernel-chosen UDP port, bound TCP on the same number and tried the kernel's next UDP port on a failure met ten refused neighbours in a row there. `TestServer_ListenPortZeroAtReservedTCPPorts` in `./internal/meshdns/` and `TestDNSStub_ListenPortZeroAtReservedTCPPorts` in `./test/e2e/mockapi/` each make a reservation of their own with `CreatePersistentTcpPortReservation`, take UDP ports until the kernel's pick has reached it, and ask the mesh DNS server and the fake resolver of its tests, or the mock API's DNS stub, for port 0; each deletes its reservation when it ends. A fixed port fails the same way on a boot that reserved it: `TestPeerRoutes_RealWintun` listened on UDP port 51994 and was refused there once, so it now takes its listen port from the kernel, which leaves out the ports reserved for UDP when it picks one for UDP. `TestPeerRoutes_RealWintunAtReservedUDPPorts` in `./internal/bridge/` pins that: it makes a reservation with `CreatePersistentUdpPortReservation`, over the ports 51900 to 51999 when they are free, takes UDP ports until the kernel has handed out the one before the reservation, and runs the peer route test, whose pick is then the one that meets the reserved ports. It creates a Wintun adapter and a route as that test does, so the step also sets `PLEXD_TEST_REAL_WINTUN` and `PLEXD_TEST_REAL_ROUTES`. The UDP pick belongs to the whole host, so `-p 1` runs the three packages one after the other. The step writes the test output to `real-ports.txt` under `RUNNER_TEMP`, exits with `go test`'s status when it failed, and fails unless the output holds the `--- PASS:` line of all three tests, a skip included.

::: v-pre
**Matrix strategy:** the job sets `runs-on: ${{ matrix.os }}` over three labels, producing the jobs `unit-test (ubuntu-latest)`, `unit-test (windows-latest)` and `unit-test (macos-latest)`.
:::

| Label            | Image                | Architecture |
|------------------|----------------------|--------------|
| `ubuntu-latest`  | Ubuntu               | x64          |
| `windows-latest` | Windows Server 2025  | x64          |
| `macos-latest`   | macOS 26             | arm64        |

`fail-fast: false` keeps a Windows failure from cancelling the Linux and macOS jobs, whose results are what tell you whether a failure is platform-specific. `timeout-minutes` is 30 rather than the usual 10: the Linux job takes about a minute and a half, and no measured Windows duration exists yet.

`-race` needs cgo everywhere except macOS, so the Windows job links against the C toolchain its runner image ships. The race detector supports windows/amd64 and both macOS architectures, which is what these three labels resolve to.

Tests that cannot run on a platform skip themselves rather than being excluded: see [Tests that cannot run everywhere](./getting-started.md#tests-that-cannot-run-everywhere).

### integration-test

Runs only test functions matching the `Integration` pattern.

| Step                   | Command / Action                                      | Purpose                                      |
|------------------------|-------------------------------------------------------|----------------------------------------------|
| Checkout               | `actions/checkout@v4`                                 | Clone repository                             |
| Setup Go               | `actions/setup-go@v5` (`go-version: '1.26'`)         | Install Go with module caching               |
| Run integration tests  | `go test -race -count=1 -run Integration ./...`       | Execute integration tests with race detection|

The `-run Integration` flag performs substring matching, selecting test functions such as `TestIntegration_*`, `TestRelayIntegration_*`, `TestBridgeReconcileIntegration_*`, and `TestUserAccessIntegration_*`. Packages with no matching tests are skipped gracefully.

## Go Version

All jobs pin Go 1.26 via `go-version: '1.26'` (not `1.26.0`), which resolves to the latest patch release. This matches the version specified in `go.mod`.

## Module Caching

`actions/setup-go@v5` automatically caches downloaded Go modules using `go.sum` as the cache key. No explicit cache configuration is needed. On cache hit, `go mod download` is skipped, reducing job duration.

## Adding a New Job

1. Add a new entry under `jobs:` in `.github/workflows/ci.yml`
2. Set `runs-on: ubuntu-latest`, or an `os` matrix with `runs-on` taken from it, when the job has to run on every platform, as `unit-test` does
3. Set `timeout-minutes` to an appropriate value (10 for standard jobs, 15 for integration tests, 30 for the cross-platform unit-test matrix)
4. Include `actions/checkout` and `actions/setup-go` pinned to full SHA hashes as the first two steps
5. Do not add a `needs:` key unless the job genuinely depends on another job's output
6. Add the job's run commands as subsequent steps
